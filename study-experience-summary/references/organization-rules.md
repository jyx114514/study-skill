# 整理细则（Organization Rules）

本文件是 study-experience-summary skill 的详细整理规范。SKILL.md 提供流程骨架，本文件提供每一步的细则、示例与检查清单。

## 1. 总体原则

- **不是流水账摘要**：不要机械按聊天消息出现的先后顺序复述。
- **按知识逻辑重组**：先读完整记录，判断包含哪些主题，再按知识之间的逻辑关系重新组织。
- **验收标准**：几个月后忘记这次聊天，只阅读这份 HTML，能快速重新理解知识 / 重新完成问题解决过程。

## 2. 学习与知识类内容的组织原则

以"帮助理解和复习"为目标，**不套用**"问题—报错—解决方案"的排错结构。

涉及：生物学名词、蛋白质/酶、代谢通路、信号通路、分子机制、数学概念、深度学习原理、算法、模型结构等。

按知识本身的逻辑灵活组织，可用结构（不要求机械使用全部章节）：

1. 核心概念
2. 基本定义
3. 组成部分
4. 工作机制 / 生物学机制
5. 过程或通路
6. 上游与下游关系
7. 关键分子 / 蛋白 / 酶 / 参数
8. 调控机制
9. 生物学意义或实际作用
10. 与相似概念的区别
11. 容易混淆的地方
12. 核心知识总结

## 3. 通路、机制和流程类知识的组织

涉及：代谢通路、信号通路、生物合成过程、分子机制、神经通路、算法流程、数据处理流程、模型工作流程。

重点整理：**起点 → 中间步骤 → 关键节点 → 调控关系 → 最终结果**。

- 不要只罗列名词。
- 让读者理解"这个过程为什么会这样发生，各个部分之间是什么关系"。
- 必要时使用箭头、流程图或 SVG 将复杂关系可视化。

## 4. 技术问题与排错内容的组织

涉及：软件、模型、本地部署、代码、环境配置、Bug、报错。

思路：**问题是什么 → 原因是什么 → 最终如何解决 → 以后如何复现**。

- 重点保存最终有效的解决方案。

## 5. 压缩试错过程

聊天记录中可能存在大量重复尝试、失败方案和排查过程。**不要逐条记录所有失败操作。**

原始聊天可能形如：

> 尝试方案 A → 失败
> 尝试方案 B → 失败
> 修改参数 → 仍然失败
> 更换版本 → 仍然失败
> 最终发现是某个配置字段导致问题

总结时应压缩为：

> 排查过程中尝试了多种方案，但均未解决问题。最终确认问题由 XXX 导致。

然后重点解释：

- XXX 是什么；
- 为什么会导致问题；
- 如何确认；
- 最终修改了什么；
- 正确操作是什么；
- 如何验证问题已经解决。

除非某个失败方案本身具有重要的警示或排错价值，否则不需要详细记录。

## 6. 技术内容需要重点保留的信息

应尽量提取：

- 使用的软件、框架或模型；
- 问题表现；
- 关键报错；
- 根本原因；
- 最终解决方案；
- 修改前后的关键差异；
- 可直接复用的命令（代码块展示）；
- 可直接复用的代码（代码块展示）；
- 配置文件中的关键参数；
- 容易再次踩坑的地方。

**路径/用户名/设备名等仅适用于当前电脑的内容**（不是解决方案本身的一部分）应写成占位符：

```text
<模型目录>
<项目目录>
<用户名>
<模型文件.gguf>
```

但**真正影响问题的版本号、参数值、报错内容等不要随意泛化**。

## 7. 追问整合原则

用户可能围绕同一知识点不断追问。例如：

> 什么是 A？
> A 和 B 有什么区别？
> 为什么 A 会导致 C？
> 那 D 在这个过程中有什么作用？
> A 和前面讲的 E 有什么关系？

**不要**把这些做成五段问答。识别它们属于同一知识体系，重新组织为连续结构：

**A 的定义 → A 与 B 的区别 → A 如何影响 C → D 的作用 → A 与 E 的关系**

## 8. 输出格式要求

**默认输出：Markdown（.md）文件。** 只有当用户明确要求 HTML（"要html"、"转成网页"、"生成网页版"等）时才输出 HTML。

### 8a. Markdown 版（默认）
- 标准 Markdown 语法：标题层级（`#`/`##`/`###`）、列表、表格、fenced code block（含语言标注）、引用块、加粗/斜体。
- 图表用 Mermaid 代码块（```mermaid：mindmap / flowchart / sequenceDiagram / timeline）。
- 重要概念和结论用加粗或引用突出；代码、命令、报错用代码块；注意事项用引用块或加粗前缀。
- 文件名以 `.md` 结尾。

### 8b. HTML 版（仅用户明确要求时）
- 独立 HTML 文件，浏览器直接打开。
- 不依赖外部 CSS 或 JavaScript；CSS 直接包含在 HTML 中。
- 正确显示中文（`<meta charset="UTF-8">`）。
- 页面结构清晰，适合长期学习笔记。
- 合理标题层级。
- 重要概念和结论突出显示。
- 代码、命令、报错、注意事项使用明显不同的视觉样式。
- 风格：简洁、专业、知识笔记、技术文档、易于复习。不加无实际意义的装饰。
- 文件名以 `.html` 结尾。

## 9. 图表要求

当图示能明显提高理解效率时添加可视化（**以帮助理解为首要目标**，不要为丰富页面强行加图）：
- **Markdown（默认）**：用 Mermaid 代码块（mindmap / flowchart LR-TD / sequenceDiagram / timeline）。
- **HTML（用户要求时）**：直接在 HTML 中嵌入 SVG。

推荐场景：

- **生物学**：代谢通路、信号通路、蛋白质相互作用、上下游调控关系、生物学过程、分子机制、细胞结构关系。
- **计算机与深度学习**：神经网络结构、Attention 机制、数据流、模型架构、算法流程。
- **技术排错**：软件组件关系、请求调用链、Bug 产生机制、修改前后对比、排查流程、文件结构。

- 图表以**帮助理解**为第一目标，不为让页面更丰富而强行加图。
- HTML 版中 SVG 直接嵌入 HTML，保持总结为单个独立 HTML 文件。

## 10. 重点信息可视化

可适当使用：流程图、对比表格、时间线、层级结构图、因果关系图、上下游关系图、"修改前 vs 修改后"、"概念 A vs 概念 B"。

尤其对于生物学通路和深度学习模型结构，仅靠文字难以形成整体认识时，应优先考虑图表辅助（MD 用 Mermaid，HTML 用 SVG）。

## 11. 信息准确性

- 原则上根据聊天记录中已有的信息进行总结。
- 不编造：未验证的原因、未执行过的命令、未确认有效的解决方案、不存在的实验或测试结果、聊天中没有依据的知识结论。
- 技术问题最终没有解决 → 明确标记：**「本次对话中尚未得到最终解决。」**
- 技术结论只是推测 → 明确标记：**「可能原因 / 推测」**。不将推测写成已确认事实。

## 12. 最终解决方案突出（技术排错类）

包含排错过程的聊天记录，若最终找到解决方法，设置明显区块：

## 最终解决方案

即使不阅读完整排查过程，也能快速知道：

- 最终原因；
- 最终修改；
- 最终命令；
- 最终配置；
- 如何验证已经解决。

## 13. 核心知识总结（学习类）

学习类内容不强行设置"最终解决方案"。在文章末尾设置：

## 核心知识总结

用简洁方式整理：

- 最重要的概念；
- 关键机制；
- 关键因果关系；
- 容易混淆的知识点；
- 最值得记忆的内容。

作为之后快速复习的入口。

## 14. 文件保存

- 保存在**当前项目文件夹**中，不保存到项目外临时目录。
- **默认输出 `.md` 文件**；用户明确要求 HTML 时输出 `.html` 文件。
- 文件名根据核心内容自动生成，示例（默认 `.md`）：

```text
糖酵解与三羧酸循环知识总结.md
MAPK信号通路机制总结.md
Attention与KV_Cache原理总结.md
Ollama_GGUF模型加载错误排查与解决.md
Qwen模型NextN兼容性问题解决.md
```

- 避免：`总结.md`、`result.md`、`output.md`、`1.md`（HTML 版同理避免 `1.html` 等）。
- 多个明显独立大主题 → 可拆分多个文档；同一知识体系 → 整合为一份完整文档。
- 项目中已存在同主题总结 → 优先更新/扩展已有文档，避免重复文件。

## 15. 交付前核对清单

生成文档后、交付前逐项自检：

- [ ] 是否按知识逻辑组织，而非聊天顺序流水账？
- [ ] 是否默认输出 `.md` 文件？（仅在用户明确要求 HTML 时才输出 `.html`）
- [ ] 同一知识体系的追问是否已整合为连续结构？
- [ ] 失败试错是否已压缩为一句概述 + 根因解释？
- [ ] 最终解决方案（若有）是否醒目且包含原因/修改/命令/配置/验证方法？
- [ ] 学习类是否以核心知识总结收尾？
- [ ] 命令/代码/配置是否用代码块展示？路径是否已泛化？
- [ ] 是否存在编造内容（未验证原因/未执行命令/未确认方案）？
- [ ] 未解决问题是否已标注"尚未得到最终解决"？推测是否已标注"可能原因"？
- [ ] HTML 是否自包含（无外部 CSS/JS 依赖）？中文显示是否正常？
- [ ] 图表（MD 用 Mermaid / HTML 用 SVG）是否只在确实有助于理解时使用？
- [ ] 文件是否保存在项目文件夹、文件名是否语义化（且扩展名与输出格式一致）？
